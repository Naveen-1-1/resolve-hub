# Application scope

**Application description:**\
ResolveHub is a full-stack customer support platform. Customers can open support sessions, browse a structured FAQ document library, and escalate unresolved issues into trackable support tickets. Support agents can manage the ticket queue and move tickets through a defined lifecycle. Knowledge administrators can manage FAQ documents and view platform monitoring metrics.
**Users / Target audience:**

- **Customer:** A customer or employee who needs help with products, policies, or procedures. Customers can start support sessions, browse FAQs, view session history, and escalate unresolved issues into tickets.
- **Support agent:** A frontline agent who handles escalated queries. Support agents can view and filter the ticket queue, assign tickets, update ticket status, review linked session context, and view notifications.
- **Knowledge administrator:** An administrator who manages the FAQ library and platform health. Knowledge administrators can create, update, and delete FAQ articles, organize them by category and tags, and view monitoring metrics.
  **Data description:**\
  ResolveHub stores and displays user accounts and roles, support-session topics and history, FAQ documents with titles, questions, answers, categories, and tags, support tickets with subjects, descriptions, priorities, statuses, assignments, and linked session context, notifications, and monitoring metrics such as session volume, ticket status, notification totals, and resolution time.
  **Main tasks / use cases:**
- T1 — Customer: Access an account, start a support session, and understand the customer dashboard.
- T2 — Customer: Search for and evaluate an FAQ, including category and tag filtering and session tracking.
- T3 — Customer: Escalate an unresolved issue into a support ticket with session context.
- T4 — Customer: Review session history, ticket status, and notifications.
- T5 — Support agent: Triage the ticket queue and select a ticket for review.
- T6 — Support agent: Review ticket and session context before taking responsibility for a ticket.
- T7 — Support agent: Assign, progress, and resolve a ticket.
- T8 — Support agent: Review and manage ticket-related notifications.
- T9 — Knowledge administrator: Understand dashboard metrics and monitoring information.
- T10 — Knowledge administrator: Find, edit, and verify an FAQ.
- T11 — Knowledge administrator: Create, verify, and delete a test FAQ.
- T12 — Knowledge administrator: Create and verify a user account and role.

### Script of the tasks to be read to participants

#### Customer tasks

- **T1 — Understand the application and access an account:** The participant interprets the homepage, identifies the customer journey, attempts the customer entry point, recovers from an incorrect login, and registers a customer account.
- **T2 — Find and evaluate an FAQ:** The participant starts a support session for a duplicate-charge problem, searches the FAQ library, uses category and tag controls, opens an answer, and checks whether the FAQ activity was saved to the session.
- **T3 — Escalate the problem:** The participant finds the option to contact an agent, creates a ticket with a subject, description, and priority, and checks whether the ticket was created with the session context.
- **T4 — Review history and notifications:** The participant reviews session history and ticket status, finds a related notification, and considers how to identify the next update or response.

#### Support-agent tasks

- **T1 — Understand and triage the queue:** The participant identifies the main work area, filters the queue by status and priority, compares tickets, and selects one for review.
- **T2 — Review ticket context:** The participant reviews the customer’s problem, session information, and available history to decide whether there is enough context to take responsibility.
- **T3 — Process a ticket:** The participant assigns the ticket, moves it into active work, resolves it, and checks the updated ticket in the queue.
- **T4 — Review notifications:** The participant identifies a ticket-update notification, marks it as read, and considers whether using a bulk read action would be safe.

#### Knowledge-administrator tasks

- **T1 — Understand the dashboard and metrics:** The participant identifies the monitoring, FAQ-management, and user-management areas, explains the metrics, and tries to investigate a metric.
- **T2 — Find and edit an FAQ:** The participant searches for an existing FAQ, tries to find additional records, edits the FAQ, saves the change, and checks whether the update persisted.
- **T3 — Create and delete a test FAQ:** The participant creates a temporary FAQ, completes its fields, verifies the record, and deletes it.
- **T4 — Create and verify a user:** The participant finds user management, creates a temporary support-agent account, selects a role, and checks whether the account and role can be verified.

### Post questionnaire Likert Scales

The scale used was 1 = very poor or very difficult and 5 = excellent or very easy.

- How intuitive was ResolveHub or the assigned dashboard?
- How well did the application support the work required for the assigned role?
- How easy was ResolveHub or the assigned dashboard to use?
- How would you rate the individual tasks for the assigned role?

## Experiment Notes

**Participant 1 — Prashanth**\
Role: Customer

### Demographics answers

- The available notes identify the participant as a customer.
- No additional demographic answers were recorded in the available notes.

### Detailed notes

- **Notes for initial approach:** The Customers card appeared clickable, but clicking it did not produce a response.
- **Notes for T1:** After entering incorrect credentials, the login message did not clearly explain how to recover. After registration, it was not immediately clear whether the customer account had been created successfully.
- **Notes for T2:** It was unclear whether the FAQ had been added to the active support session. The category and tag filters appeared too similar, making their different purposes unclear.
- **Notes for T3:** After submitting the ticket, there was no clear confirmation that the ticket had been created.
- **Notes for T4:** The progression between ticket statuses was unclear. The meaning of each ticket status and what would happen next were not obvious. The expected response time or ETA for the ticket was not clear. Notifications did not clearly identify which ticket or support session they belonged to.
- **General feedback:** Notifications should be linked to the relevant ticket and support session. Notification-related content should appear at the top of the page instead of the bottom.

- **Intuitiveness:** “How intuitive was ResolveHub overall?” — **3/5**
- **Functionality:** “How well did the application support what you needed to do?” — **3/5**
- **Ease of use:** “How easy was ResolveHub for you to use?” — **4/5**

# Prioritized list of issues and corresponding changes:

The following list includes all distinct suggestions recorded in the participant notes, ordered by user workflow: customer, support agent, and knowledge administrator.

**1. Issue:** The Customers card appears clickable but does not respond.\
**Change:** Make the customer role entry point clearly navigate to the customer registration or login flow. Update `frontend/src/pages/HomePage.jsx` without redesigning the homepage.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. Each role card is now a semantic article with a clearly labeled router-link CTA. The customer CTA opens the registration flow, while support-agent and administrator CTAs open the login flow. The entire card is not treated as a link, so the visible action target is unambiguous.

**2. Issue:** The customer login flow does not clearly guide users who either entered incorrect credentials or do not have an account yet.\
**Change:** Keep the existing login and registration APIs. Add clear guidance to the existing login error state in `frontend/src/pages/LoginPage.jsx`, make the “New customer? Register” path prominent, and explain that existing users should retry their credentials. Keep the error generic rather than revealing whether a specific email exists.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. The existing login and registration APIs were preserved. The login page now clearly presents the Register path and shows generic recovery guidance for failed login attempts.

**3. Issue:** Registration does not clearly confirm account creation.\
**Change:** Add a small success message showing that registration succeeded, confirming the customer role and next step in `frontend/src/pages/RegisterPage.jsx`.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. Registration now passes a success notice to the customer dashboard, confirming account creation and the next step through a success popup.

**4. Issue:** Customers cannot tell whether an FAQ was added to the active session.\
**Change:** Show a visible “Viewed in this session” state after the existing FAQ tracking action in `frontend/src/components/FaqBrowser.jsx` and `frontend/src/components/SessionPanel.jsx`. Focus the answer area after an FAQ is opened.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. FAQ cards now show “Viewed in this session,” the answer area is brought into view after selection, and the FAQ browser displays confirmation after the existing tracking request succeeds.

**5. Issue:** Category and tag filters appear too similar.\
**Change:** Add short helper text or clearer labels explaining the different purposes of categories and tags in `frontend/src/components/FaqBrowser.jsx`.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. Category and tag controls now include helper text explaining their different purposes.

**6. Issue:** Customers cannot clearly confirm that a ticket was created.\
**Change:** Add a success popup after the existing ticket-creation request in `frontend/src/components/SessionPanel.jsx`, then focus the customer ticket list.\
**Priority:** **Must**\
**Was it implemented? How:** Implemented. The session panel now shows a success popup after a ticket is created and brings the customer ticket list into view while preserving the existing escalation API.

**7. Issue:** Ticket statuses and their progression are unclear to customers.\
**Change:** Add a progress bar with status “pit stops” for the existing lifecycle—Open, In Progress, and Resolved—in `frontend/src/components/TicketList.jsx` and `frontend/src/pages/CustomerDashboard.jsx`. Highlight the current status and add plain-language descriptions without changing the backend workflow.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. Customer tickets now display a shared Open, In progress, and Resolved progress indicator with the current status highlighted.

**8. Issue:** Notification content is difficult to find on the page.\
**Change:** Make the existing notification area easy to find while preserving the primary workflow on each dashboard in `frontend/src/pages/CustomerDashboard.jsx` and `frontend/src/pages/AgentDashboard.jsx`.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented with role-specific prioritization. Customer notifications appear in the top row beside the active support-session panel. Agent notifications appear in a dedicated panel after the ticket queue and detail area so ticket triage remains the primary task. Both views expose ticket context and direct ticket navigation.

**9. Issue:** The word “Review” is misleading as the action for opening a ticket.\
**Change:** Use a clearer label, such as “Open ticket” or “View ticket,” for the existing action in `frontend/src/pages/AgentDashboard.jsx`. Keep the interaction pattern consistent with the label and focus the ticket detail section after selection.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. The queue action now uses the clearer “Open ticket” label and focuses the ticket detail section after selection.

**10. Issue:** The agent queue needs both status and priority filtering, plus a way to sort tickets by status.\
**Change:** Keep the existing Status and Priority dropdown filters and add a separate Sort queue by control with Status sorting. Place the queue controls before the ticket work area so the agent can configure the primary task immediately. Do not replace the queue with a new navigation system.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. Status and Priority filters now appear in a clearly grouped control panel before the ticket queue, and the queue can be sorted by Recently updated, Status, or Priority.

**11. Issue:** The support agent does not have enough session context.\
**Change:** Display the ticket status explicitly alongside the existing progress indicator, session topic, viewed-FAQ information, and available prior activity in `frontend/src/pages/AgentDashboard.jsx`. Extend the API only where the required stored data already exists.\
**Priority:** **Should**\
**Was it implemented? How:** Implemented. The agent detail view now presents the explicit ticket status, available session topic, FAQ-view count, and session start time in a clear context summary using the existing API data.

**12. Issue:** Ticket assignment does not feel definitive and ownership terminology is unclear.\
**Change:** Use one consistent ownership label, show the assigned agent after “Assign ticket to me” succeeds, and add confirmation without changing the existing assignment rules in `routes/tickets.js`.\
**Priority:** **Must**\
**Was it implemented? How:** Implemented. The existing assignment rules remain unchanged, while the interface now uses clearer assignment wording, shows the assigned agent, and confirms successful assignment.

**13. Issue:** The next status in the support-agent workflow is not obvious.\
**Change:** Keep the existing `open → in_progress → resolved` lifecycle and add a compact progress indicator with the next valid action in `frontend/src/pages/AgentDashboard.jsx`.\
**Priority:** **Must**\
